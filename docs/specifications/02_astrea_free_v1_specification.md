1. 本仕様書の目的
本書は、If Professional ASTREA FREE v1の開発着工前仕様を定義する。
商品思想については「If Professional ASTREA 開発コンセプト」を最上位原則とし、本書ではその思想をTheme、Core、管理画面、各種Patternおよび品質要件へ具体化する。
ASTREA FREEはPROの体験版ではなく、FREE単体で本番運用可能な専門家サイトを構築できる製品とする。PROとの差は機能制限ではなく、ユーザー自身が行う作業を専門職向けに自動化する点に置く。
________________________________________
2. UX基本原則
ASTREAを使うこと自体を目的にしない。
ASTREAは専門家が集客し、仕事につなげるための道具である。
したがって、設定を完璧にするために公開を遅らせない。
基本思想は、
60点で公開できる。必要になったら後から育てられる。
とする。
なお「60点」はユーザーへ要求する設定量についての考え方であり、製品品質を60点でよいとする意味ではない。
設定項目は原則として、
•	必須：公開に必要な最低限 
•	推奨：設定するとより良いが後回し可能 
•	詳細：必要なユーザーのみ 
の3段階で考える。
一度入力した情報は可能な限り再利用し、同じ情報を複数箇所で入力・修正させない。この原則は既存の開発コンセプトにも明記されている。
________________________________________
3. 製品構成
ASTREA Theme
主に表示を担当する。
Templates、Template Parts、Patterns、Style Variations、Design System、Responsive表現等を担当する。
ASTREA ThemeはCoreのインストール・有効化を強制しない。Coreが存在しない、または無効化されている場合でも、Theme単体でWordPress Block Themeとして安全に動作し、PHP Fatal等を発生させない。
ASTREA Core
テーマ変更後も保持すべき情報およびサイト共通機能を担当する。
Office Profile、営業時間、CTA、問い合わせ、FAQ、Service、Price、CASE、SEO、OGP、GA4、共通設定等をCore側へ置く。
ThemeとCoreを分離する基本構造は既存企画書でも定義済み。

【2026-08-26 Decision 021により確定】ASTREA Coreは任意Pluginとする。ただし、ASTREAの主要機能を利用するための公式推奨Pluginとして位置付ける。Office Profile、Service、Price、FAQ、Contact、SEO / OGP、Search Console支援、Coreデータ再利用、セットアップ支援等、ASTREA Coreが責任を持つ機能は、Coreを有効化した場合に利用可能となる。基本原則は「Coreは推奨する。しかしThemeを人質にしない。」
Profession PRO
FREEに掛けた制限を解除する製品ではない。
FREEユーザーが自分で行うページ作成、サイト構成、Navigation、デザイン設定等を職種知識に基づいて自動化する。
既存比較仕様でもFREE＝手動、PRO＝自動化として整理されている。
Booking
予約機能はASTREA Coreへ含めない。
利用しない事務所も多く、日時・枠管理等によって処理も大きくなるため、将来の別Pluginとする。
________________________________________
4. ASTREA Core ― 情報一元管理
Coreをサイト情報の正本とする。
同じ情報を、
「HOMEにも入力」
「Footerにも入力」
「Accessにも入力」
とはしない。
Coreの情報を各表示場所から参照する。
代表的な情報として、
事務所情報、代表者情報、資格・所属、住所、電話、営業時間、定休日、臨時休業、アクセス、相談方法、CTA、SNS等
を管理する。
年末年始、夏季休業、臨時休業にも対応する。
営業カレンダーは当月営業状況を分かりやすく確認できる表示を想定するが、予約機能とは分離する。

【2026-08-26 Decision 022により確定】上記の一元管理対象は、以下のように責任範囲を分離する。

- **Office Profile**（Construction Order 002で実装済み）：事務所名、住所、電話、営業時間、定休日、臨時休業、SNS等。事務所・法人・専門家組織そのものの情報。個人事務所・士業法人（複数専門家が所属する事務所）のいずれにも対応する。**代表者名は含まない**（下記参照）。
- **Professional Profile**（§8参照、Construction Order 003で実装済み）：資格・所属・経歴等、専門家個人に紐づく情報。Office 1に対しProfessional Profileは0〜複数人を扱える構造とする。
- **CTA・相談方法**：Office Profile / Professional Profileのいずれにも含めず、別責任（CTA / Consultation）として扱う。
- **アクセス固有情報**（最寄駅・徒歩時間・駐車場等、§13参照）：Office Profileには含めず、ACCESSの責任とする。所在地そのものはOffice Profileを正本として再利用する。

【2026-08-26 Decision 023により確定】代表者は「人」に属する情報であり、Office Profileの管轄ではない。代表者情報の正本はProfessional Profileとし、Professional Profileに代表者識別（`is_representative`）を持たせる（§8参照）。既存のOffice Profile「代表者名」は廃止し、Construction Order 003AでSchema Migrationを実施した（旧データは`legacy_representative_name`として保全し、自動的な人物生成は行わない）。複数の専門家を代表者として同時に指定できるかどうかは一意制約を設けず、要確認事項として残している。
________________________________________
5. Design System
ASTREA FREEの最大級の競争力はデザイン品質とする。
「無料だから多少ダサくてもよい」は認めない。
無料であることは購入理由ではなく付加価値であり、価格表示を見なくてもASTREAそのものが選ばれる品質を目標とする。
2027年公開時には、その時点のWebデザイン、Typography、UI、Accessibility、WordPress技術動向を再調査する。流行を取り入れながらも、Style Variation、Patterns、Design Systemによって将来更新可能な構造とする。これは開発コンセプトでも明示済み。
Patternは数を目的にしない。
少数精鋭で、採用するすべてを一級品にする。
またコンテンツ数をデザイン都合で強制しない。
「サービスを3件登録しないと成立しない」等は禁止する。
1件でも10件でも、それぞれ適切に成立させる。
________________________________________
6. HOME
HOMEは固定された完成テンプレートではなく、Patternを組み合わせて構築できるものとする。
代表的な構成要素として、
Hero、Trust、Services、Profile、Flow、Price、FAQ、CASE、Access、CTA等を用意する。
すべてを使用する必要はない。
開業直後でCASEが存在しない場合などでも、空白や不自然な構成にならない。
________________________________________
7. SERVICES
ASTREA FREEは全士業共通版であるため、職種固有のサービス内容を持たない。
ユーザー自身がServiceを登録する。
Service情報はHOME、サービス一覧、個別Service、関連FAQ、CASE、記事等から再利用可能な構造とする。
専門用語だけでなく、依頼者の立場から分かりやすい表現を使うことを編集ガイドで支援する。
職種固有のService生成はPROの担当とする。
________________________________________
8. PROFILE
専門家本人を信用材料として適切に紹介できる構造とする。
写真、氏名、資格・肩書、紹介文等を基本とし、必要に応じて、
経歴、学歴、所属、登録情報等
も掲載可能とする。
ただしすべて任意とし、項目を埋めなければデザインが成立しない構造にはしない。

【2026-08-26 Decision 022により確定】本項の情報を「Professional Profile」と呼ぶ。事務所・法人そのものの情報（Office Profile、§4参照）とは責任範囲を分離する。個人事務所では通常1人、士業法人・複数専門家事務所では複数人を登録・表示できる、0〜複数人対応の構造として設計する。**Construction Order 003で実装済み**（Custom Post Type + Post Meta）。

【2026-08-26 Decision 023により確定】Professional Profileに、その人物が代表者であることを識別するフラグ（is_representative）を持たせる。代表者情報の正本はOffice Profileではなく本項とする。具体的な肩書テキスト（代表社員・所長・代表税理士等）は「資格・肩書」項目へ入力し、肩書専用の新しい項目は追加しない。複数人を代表者として指定できるかどうかは一意制約を設けていない（要確認事項）。**Construction Order 003Aで実装済み。**
________________________________________
9. FLOW
相談から依頼までの流れを表示する。
件数固定にはせず、少ないステップでも多いステップでも成立させる。
専門職固有の手続フローそのものはFREEへ内蔵しない。
________________________________________
10. PRICE
料金情報は一元管理する。
固定額、○円～、月額、時間制、無料、個別見積、自由表記等へ対応する。
料金グループ、実費・追加費用等の注記も任意で扱える。
HOME、Priceページ、Service等から同じ料金情報を参照できる構造とし、金額変更時に複数ページを修正させない。
士業固有の料金体系はFREEへ内蔵しない。
________________________________________
11. FAQ
FAQをCoreで一元管理する。
主な情報は、
質問、回答、カテゴリ、関連Service、表示順、公開状態、重要FAQ
とする。
同じFAQをHOME、FAQ一覧、Serviceページ等で再利用する。
FAQ件数を強制しない。
少数ならMinimal表示、多数ならカテゴリ表示等、件数に適したPatternを用意する。
FAQはSEOのための量産装置にはしない。
依頼者の疑問を解消することを第一目的とする。
________________________________________
12. CASE / RESULTS / VOICE
3種類を区別する。
CASE＝対応事例
RESULTS＝公開可能な実績・数字
VOICE＝お客様の声
すべて任意。
開業初日で0件でもサイトデザインが成立する。
CASEはService等との関連付けを可能とする。
VOICEについては掲載許可確認を支援するUIを検討する。
ASTREA自身が法的な掲載可否を判断するものではなく、守秘義務、個人情報、所属団体等の規則を確認するよう案内する。
________________________________________
13. ACCESS
Coreに登録された住所、営業時間、最寄駅、徒歩時間、駐車場、臨時休業等を再利用する。
Accessページで同じ情報を再入力させない。

【2026-08-26 Decision 022により確定】住所・営業時間・臨時休業はOffice Profile（§4、Construction Order 002で実装済み）を正本として再利用する。最寄駅・徒歩時間・駐車場等のACCESSページ固有情報は、Office Profileには含めず、ACCESSの責任範囲で別途管理する（未実装）。
地図は、
ページ内表示 / Google Mapsで開く / 地図なし
等から選択可能にする方向。
外部地図サービスへの過剰依存を避ける。
スマートフォンでは地図・電話・経路等への操作性を重視する。
________________________________________
14. Header / Navigation / Footer
Headerは少数精鋭のPatternを用意する。
Standard、Minimal、Center、Editorial、CTA強調等を候補とする。
スマートフォンHeaderはPC版を単純縮小せず、情報の優先順位を再設計する。
Mobile CTAは任意。
Footerも単なる余り情報置き場とせず、サイト最後の一画面としてデザインする。
事務所情報・電話・営業時間・CTA等はCoreから取得する。
情報を編集する場所と、表示する場所を分離する。
________________________________________
15. CONTACT
通常問い合わせはASTREA Core FREEへ含める。
予約とは分離する。
標準フォームはフォームビルダー化せず、
名前、メール、電話、件名、問い合わせ内容、Privacy Policy同意
等の基本項目を中心とする。
入力→確認→送信→完了の一般的な導線を提供する。
使用・必須・任意程度の設定は可能とする。
Nonce、Honeypot、入力検証、Sanitization、連続送信抑制（Rate Limit）等のスパム・セキュリティ対策を標準搭載する（外部CAPTCHAは必須としない）。曖昧なSpam判定のみを理由に正規の問い合わせを無断削除しない。

【2026-08-25 Decision 003・004・005・006・007により更新】
問い合わせはWordPress標準のメール送信機構（`wp_mail()`等）で通知する。Project-if独自のメール配送サーバーは必須としない。通知先メールアドレスの登録・変更時は、確認メール＋一回限りTokenの確認URLにより受信可能性を確認する。

問い合わせは送信時点でCoreへ即時保存する（メール配送の成否に関わらず保存する）。保存期間は10 / 30 / 60 / 90日から選択でき、初期値は30日。保存期間経過後は自動削除する。

管理画面には問い合わせ一覧、未確認状態、未確認件数を表示する。通知タイミングは即時通知 / 指定時刻のまとめ通知から選択可能とし、初期値は即時通知とする。

FREE v1では問い合わせ機能をCRM化しない（高度な検索・顧客管理・案件管理は作らない）。適切な権限を持つユーザーはCSV一括Exportができる。

個人情報を不必要にWordPress DBへ蓄積しない方針は維持するが、保存期間を区切った一時保存によって「メール不達で相談が消失する」リスクを回避する（詳細は`04_astrea_free_v1_preconstruction_decisions.md` Decision 003〜007）。

外部フォームPluginや外部URLへの切替も可能とし、ASTREAへロックインしない。
________________________________________
16. SEO Foundation
ASTREA FREE単体で、基本的な本番SEO運用が可能な状態を目標とする。
別SEO Pluginを必須としない。
対象候補は、
title、meta description、canonical、robots、OGP、Breadcrumb、基本構造化データ、Search Console認証、XML Sitemap
等。
Sitemapは自動管理を基本とする。
WordPress標準機能で適切に実現できるものは標準を活用し、不必要な独自実装を避ける。
SEOを知らないユーザーでも基本的に妥当な状態になるよう自動判断し、詳細設定は上級者向けとする。SEO設定で100点を追わせず、短時間で必要十分な状態にして集客活動へ進ませることを優先する（Decision 008）。
他SEO Pluginを利用したいユーザーについては二重出力を避け、邪魔をしない。この方針はSEO Plugin以外の主要な第三者Pluginとの競合可能性にも一般化し、既知の競合事例が判明したものをUpdateで検出リストへ追加できる運用とする。未知Pluginを推測で制御しない（Decision 018）。

【2026-08-25 Decision 010により更新】Breadcrumbは、視覚的なBreadcrumb UI（Theme側で表示）と、検索エンジン向けのBreadcrumbList構造化データ（Core側でJSON-LD出力）の両方を標準対応する。WordPress標準の投稿階層・分類（Taxonomy）を利用し、Breadcrumb専用の独自データ正本は作らない。過剰なユーザー設定は要求しない。
________________________________________
17. OGP
サイト標準OGP画像を設定可能とする。
ページ個別画像等が存在する場合のFallback順序を定義する。
画像アップロード画面では、その時点で推奨される画像サイズ・比率等を必ずその場で案内する。
推奨サイズから大きく外れる画像には穏やかな警告を表示できるよう検討する。
SEOスコア等でユーザーを採点するUIにはしない。
________________________________________
18. GA4 / Search Console
管理画面から簡単に設定可能とする。
ユーザー自身にHTMLやJavaScript編集を要求しない。
使わない場合は関連処理を読み込まない。
既存企画書でもGA4・SEOはASTREA Coreの責任範囲として定義されている。

【2026-08-25 Decision 009により更新】Search Consoleの実装範囲はHTMLタグ方式による所有権確認の支援に限定する。Search Console API、OAuth連携、検索順位分析等は作らない。GA4による所有権確認が可能な場合は案内してよいが前提にはしない。WordPress標準のXML Sitemap URLとSearch Consoleへの登録手順を案内する。
________________________________________
19. BLOG / NEWS
ブログを書くことを公開条件にしない。
記事0件でも問題なくサイトを公開できる。
情報発信を始めた場合は集客手段として十分使える品質を提供する。
NEWSとコラム/BLOGを訪問者に分かりやすく区別できるようにするが、v1から不必要な独自投稿タイプを量産しない。
WordPress標準投稿機能を最大限利用する。
記事Typographyは長文でも読みやすいことを最優先する。
記事とService、FAQ、CASE等を関連付け、自然な内部導線を作れる構造を目指す。
________________________________________
20. ARCHIVE / SEARCH / 404
Archiveは記事数が少なくても多くても成立する。
Search結果では該当コンテンツを分かりやすく表示し、0件の場合もService一覧等の次の行動を提示する。
404ページもASTREA Design Systemの一部として設計し、HOMEや主要ページへ自然に戻れるようにする。
________________________________________
21. 初回セットアップ
テーマ有効化直後に設定地獄へ放り込まない。
初回案内はスキップ可能とする。
基本フローは、
基本情報 → 問い合わせ方法 → デザイン → 推奨サイト構成 → 準備完了
程度に留める。
FREEではページを自動生成するのではなく、ユーザーへ「次に何をすればいいか」を案内する。
既存資料で定義された、インストールから公開までの一本道とも整合させる。
________________________________________
22. ASTREA Dashboard
WordPress標準機能を隠すのではなく、ユーザーが迷わない入口を提供する。
Dashboardから、
事務所情報、専門家情報、営業時間、問い合わせ、SEO・計測、デザイン、ページ制作等
へ移動できる。
設定状況は点数化せず、
完了 / 推奨 / 任意
程度のチェックリストで案内する。
「全部埋めないと完成ではない」というUXにはしない。
________________________________________
23. Responsive
PCデザインを縮小したものをスマートフォン版としない。
Hero、Service、Price、Flow、Header等は画面サイズに応じて情報優先順位・レイアウトを再設計する。
端末固有CSSの増殖を避け、Fluid Typography、柔軟なGrid、少数のBreakpoint等を基本とする。
________________________________________
24. Accessibility
テーマ側で対応可能なものをユーザー設定へ丸投げしない。
キーボード操作、Focus表示、HTML構造、見出し階層、Form Label、alt、Contrast、Skip Link、適切なARIA等を品質要件とする。
Animationを使用する場合はprefers-reduced-motion等を尊重する。
________________________________________
25. Performance
高速化Pluginを前提にしない。
ASTREA Theme + ASTREA Coreの標準構成そのものを軽量にする。
必要なCSS・JSのみ読み込み、外部ライブラリを安易に増やさない。
使用していない外部サービス関連処理を読み込まない。
画像についてはWordPress標準のResponsive Image、lazy loading等を尊重する。
公開時点のCore Web Vitals等を確認するが、100点取得ゲームにはしない。
________________________________________
26. Update
更新によって既存サイトを勝手に作り替えない。
新Pattern追加＝新しく選択可能になるのであり、既存サイトへの強制適用ではない。
既存企画書でもWordPress標準に近い更新体験を目指し、Project-if側障害で既存サイトを停止させないことが定義されている。

【2026-08-25 Decision 014により更新・確定】Theme、Template、Template Part、Style Variation等の更新とユーザーカスタマイズの関係は次の通り確定する。通常の設定・Coreデータを不必要に破壊しない設計とし、Templateへユーザーデータを直接固定しすぎず、Styles / Core / Binding / WordPress標準設定へ適切に分離する。Site Editor等でユーザーがTemplate / Template Partを独自構造編集した場合は、WordPress標準挙動（DB保存されたユーザー版がThemeファイルより優先される）を尊重し、強制上書きしない。ASTREA自身のBug・Security・必要なCompatibility問題は修正し、最新版として提供する。
________________________________________
27. データ保持・アンインストール
Theme変更後も意味を持つ情報はCoreへ保存する。
Core停止とデータ削除を区別する。
停止 ≠ 削除。
Core削除時も保存データを無条件に消さない。
完全削除はユーザーの明示操作と確認を必要とする。
将来的なExport / Importも考慮できるデータ構造を検討する。
________________________________________
28. ロックイン防止
ASTREA固有Shortcode等を不必要に乱造しない。
可能な限りWordPress Core Blocks、標準HTML、標準投稿データを利用する。
テーマ変更後にASTREA専用記法の残骸が大量に残る構造を避ける。
これは開発コンセプトにある「ユーザーのコンテンツを人質に取らない」という原則を実装へ落とすものである。
________________________________________
29. Compatibility / Migration
【2026-08-25 Decision 020により確定】対応バージョンは、PHP 8.3以上を1.0の初期最低ラインとする。WordPressは7.0以上を初期Targetとし、7.1を主開発・Test基準とする。標準API利用上7.0対応が明確な不利益となる場合は1.0公開前に7.1以上へ引き上げ可能とする。新PHP対応の追加と旧PHP対応の終了は別々に判断し、新対応追加のみを理由に旧対応を即座に切らない。ASTREA自身のPHP互換性は製品保守対象とするが、第三者Plugin固有のPHP互換性はサポート対象外とする。
新WordPressバージョン公開時には互換性確認を行う。
CoreのDB構造変更にはSchema Version等によるMigration管理を導入する方向とする（具体的な実装機構は実装フェーズで設計する）。
非推奨機能は突然削除せず、既存ユーザーへの影響を考慮して移行期間・代替手段を設ける。

30. 品質管理
リリース品質を人間の記憶だけに依存させない。
可能な範囲で、
Coding Standards / Theme Check / Accessibility / Responsive / Performance / PHP・WordPress Compatibility等
を自動検査・CIへ組み込む。
「リリース前にコデちゃんが覚えていたら確認する」は品質管理方式として採用しないｗ

31. ASTREA FREE v1でやらないこと
ここも正式仕様として残した方がいい。
職種固有ページの自動生成
→ PRO
専門職固有のサイト構成判断
→ PRO
Navigation自動構築
→ PRO
大規模変更前Backup / Restore
→ PRO
予約管理
→ 別Plugin
高度なフォームビルダー
→ ASTREAの責任外
問い合わせの高度な検索・顧客管理・案件管理（CRM化）
→ FREE v1では行わない（ただし送信時点でのCore一時保存、一覧表示、CSV Exportは行う。Decision 004〜006）
SEOスコアゲーム
→ 行わない
FAQ・地域ページ等のSEO目的大量生成
→ 行わない
Marketing素材の継続配信
→ 将来Subscription
既存の商品構造でもFREE＝作れる、PRO＝作ってくれる、Marketing＝作った後の集客支援として分離されている。

32. v1完成判定
ASTREA FREE v1は、
専門家がFREEだけを使って、本番公開できる品質のサイトを、自分自身で構築できること。
を完成条件とする。
機能数では判定しない。
デザイン、Core一元管理、問い合わせ、基本SEO、Responsive、Accessibility、Performance、更新安全性まで含めて、「無料でなくても選びたい」と思える状態を目標とする。
そして迷ったら開発コンセプトへ戻る。
FREEは、作れる。
PROは、作ってくれる。
